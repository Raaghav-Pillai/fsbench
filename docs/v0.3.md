# FSBench v0.3: realistic candidate tasks and validity tooling

FSBench now separates **Synthetic** controlled worlds from **Realistic** authored workplace scenarios. The realistic-v1 pack is a candidate awaiting actual human review and baselines. It should not be presented as externally validated or published solely because its automated checks pass.

## Pack and capabilities

There are five domains with five templates each:

| Domain | Templates |
|---|---|
| Small business finance | unpaid invoices; outstanding balance with credits; latest posted invoice; payment-summary workflow; contractual payment compliance |
| Legal/contracts | amended current terms; effective renewal date; current/previous terms comparison; authoritative agreement; terms provenance |
| HR | current manager; payroll reconciliation; latest approved review; onboarding workflow; manager-change provenance |
| Research/analysis | claim provenance; number reconstruction; issued analysis selection; estimate comparison; data-coverage reconciliation |
| Engineering | accepted benchmark result; configuration provenance; run comparison; regression-policy check; summary workflow |

Capability tags are `retrieval`, `multi_file_reasoning`, `source_selection`, `reconciliation`, `workflow_execution`, `provenance`, and `temporal_reasoning`. Existing synthetic tasks are mapped into this taxonomy. Realistic worlds combine PDF, XLSX, CSV, DOCX, JSON and text logs with signed documents, amendments, drafts, posted ledgers and raw logs. Boolean tasks include both outcomes across worlds. All data is fictional.

Each world supplies five sibling tasks over identical initial workspace bytes. Light/routine/dense conditions change clutter and copies while preserving task facts, answers and required document identities. They are authoring labels; empirical difficulty remains unknown until observations exist. Filesystem modification times are deterministic and can be misleading; synthetic creation times are recorded in the visible File activity.csv because portable filesystem creation-time control is unavailable. Realistic interfaces add `stat_file`; synthetic tool schemas remain unchanged.

## Build, hold out and validate

```powershell
fsbench build-benchmark --task-pack realistic-v1 --num-worlds 100 --out datasets/realistic-v1
fsbench validate-benchmark --benchmark realistic-v1 --root datasets/realistic-v1
fsbench benchmark-card --root datasets/realistic-v1 --out BENCHMARK_CARD.md
```

The default design creates 500 task instances across 100 distinct generated worlds, split 60/20/20 worlds into dev/validation/test. Splits are by world, never by sibling task. Secure random seeds are retained under `.private/seeds.json` for authorized reproduction. Supply `--seed-file` with a list of distinct nonnegative integers to reproduce a pack; use high-entropy private seeds for held-out data and do not reuse public dev seeds. Output datasets are immutable and are not overwritten.

```powershell
fsbench build-testset --task-pack realistic-v1 --num-worlds 100 `
  --seed-file private_seeds.json --out datasets/heldout-realistic-v1
```

Held-out task directories contain a visible task, workspace, and opaque evaluator reference. Their manifests and generation seeds live separately in `.private/manifests`, or an evaluator-owned location configured with `FSBENCH_EVALUATOR_ROOT`. Run metadata contains opaque world identities, not held-out generation seeds. Agent tools expose only the workspace. Default developer `inspect` and `oracle` commands refuse held-out labels without explicit `--evaluator`; this is workflow separation, not protection from an administrator with unrestricted local disk access. Keep private storage, hidden test workspaces and raw evaluator results off public releases.

`fsbench/packs/realistic-v1.json` pins the recipe. Changing task-generating code invalidates that lock and requires a new benchmark version. Software changes use `package_version` separately from `benchmark_version`; pre-versioning synthetic artifacts are marked `synthetic-legacy` instead of retroactively asserting a known benchmark version.

Validation checks actual file inventory, byte hashes and timestamps; parsing; required evidence; index inventory; traversal confinement; structural answer-label leakage; cross-level answer invariance; and a content-derived oracle for all 25 templates. That oracle reads extracted visible evidence and computes answers independently of stored ground truth. It is given source identities, so its success checks solvability rather than search difficulty. Release coverage gates require five domains, five templates per domain, at least 100 worlds, multiple levels, held-out splits and passing automated checks. Human validity remains a separate pending claim.

## Evidence scoring

Realistic tasks return `{"answer": ..., "evidence": ["relative/path", ...]}`; `sources` is also accepted for citations. Semantic success is separate from `evidence_precision` and `evidence_recall`. Markdown links, Windows separators, case differences, line-number suffixes and unambiguous basenames are normalized. Duplicate copies count as the same document identity. Ambiguous basenames and nonexistent files do not receive attribution credit. Incorrect citation formatting never changes an otherwise correct semantic answer.

Provenance tasks require the complete source set, including intermediate reports or execution records when specified. This scores evidence attribution, not the model's hidden reasoning process. Workflow tasks are judged by the produced CSV contents rather than by merely claiming that a file was written.

## Prepared first study

```powershell
fsbench prepare-study --root datasets/realistic-v1/validation --worlds 20 `
  --families source_selection provenance multi_file_reasoning `
  --out runs/realistic-study/study.json
fsbench run --envs datasets/realistic-v1/validation --study runs/realistic-study/study.json `
  --model openai/gpt-4o-mini --model SECOND_MODEL --model THIRD_MODEL `
  --toolset files --temperature 0 --order-seed 7 --out runs/realistic-study/models
fsbench evaluate --runs runs/realistic-study/models --paired --out runs/realistic-study/results.csv
```

This selects 60 distinct task instances from 20 worlds, balanced across five domains, for 180 model runs once three model IDs are selected. Models reuse identical environments. Pairing for realistic studies checks the actual planned cells for each world; it does not demand that naturally different worlds have every authored difficulty level. Do not interpret this observational profile comparison as a filename-only causal intervention. The current study is prepared, not executed: the other two model choices and human participants have not been supplied.

## Humans and empirical calibration

Use `human-run` for voluntary pseudonymous collection and `calibrate` for observed summaries. See the [human protocol](human-protocol.md) for a 10–20-session pilot, review questions, counterbalancing, participant/world dependence, optional ratings and privacy practices. CLI actions are instrumented; native file/search histories are self-reported. Final-answer timing excludes retrospective citation and difficulty questions. Unknown observations remain null. No human results are simulated, and human tokens are not compared.

## Contributing

Start with a concrete workplace request and document what evidence would be sufficient, where ambiguity arises, and how an independent reader can determine authority. Add a template, independent content-oracle logic, wrong-source and citation tests, and cross-difficulty invariance checks. Revise the benchmark version for task-data changes. Submit domain-review feedback or genuine pseudonymous pilot observations using the [README contribution process](../README.md#help-out). Do not submit employer files or personal information.
